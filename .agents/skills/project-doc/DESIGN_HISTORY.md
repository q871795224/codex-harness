# project-doc Skill 设计沿革

本文供维护者回顾设计取舍，说明为什么形成当前规则，避免未来迭代时重复走回已经讨论过的路径。日常 Agent 执行以 [SKILL.md](SKILL.md) 为准；本文不加入 Skill 的默认阅读流程，也不随项目正文注入会话。

记录依据为 2026-11-04 至 2026-11-05 的项目文档插件改进讨论，以及对应源码和 PR。此阶段改动汇集在 [PR #150](https://github.com/q871795224/codex-harness/pull/150)，由用户决定何时统一合并、发布。设计沿革保留当时的背景和取舍，后续变化按日期补记，执行规则继续维护在 SKILL.md。

## 2026-11-04：追加式日志暴露的问题

AIOps 项目多轮推进后，旧结论、后续纠正、阶段授权和待办混在长文中。整理前 seq 279 的正文约 257 KB，Status 为空；仅靠继续追加，Agent 需要从整段历史里推断当前生效的规则。Health Check、Naming 等事项的进展已变化，旧问题仍可能留在待办区。

同步规则是具体例子：早期约定包含 add/update/remove，后续又改为只补缺失项、保留目标独有数据。把新规则再追加一次可以保留过程，但缺少明确关系时，新会话仍可能读到两套规则。

这次讨论把目标定为“有历史可追溯的当前项目记忆”：既维护当前全貌，也保留过去的失败、纠正和决定来源。原始改进清单中的分层注入、决定状态、待办闭环、证据索引等是候选方向，不能直接视为全部已经采用的要求。

### 旧归档入口为什么下线

本轮调研看到的持久化记录包含 379 次 Agent 追加，来自 33 个会话、涉及 11 个项目；旧“归档到项目”有一条成功归档记录。用户日常主要依赖 Agent 主动记录，旧按钮需要另起模型总结最近若干轮，再审阅 Status 草稿，长期没有成为主要维护入口。

因此移除输入框、回答操作行的旧按钮和旧流程专属设置，底层实现与历史草稿处理暂留。Agent 日常记录和整文精简继续使用。调研也发现聊天结论漏记的实例，所以这里的取舍包含两部分：减少少用的入口，同时完善 Skill 的记录时机；没有承诺主动追加能够自动补齐全部聊天内容。

### 一次需要记住的现状判断失误

讨论中曾只查看较旧的工作分支，误判“归档并精简”尚未实现。核对最新分支和 [PR #146](https://github.com/q871795224/codex-harness/pull/146) 后才确认已有整文精简与历史恢复。以后评估改进点，需要先确认所看的源码分支和目标运行版本，避免把旧 checkout 的缺失重复列为新需求。

## 2026-11-05：选择简单、可追溯的维护方式

| 讨论点 | 采用的方式 | 当时的理由 |
| --- | --- | --- |
| 默认注入量 | 保留全文注入，10,000 tokens 作为可配置门限；超过门限才排除明确软删除、被替代或撤销的受管理条目 | 用户认为先判断哪些摘要该注入、再按需检索其余内容，会增加筛选与查找复杂度；当前完整上下文仍可接受 |
| 错误和旧决定 | 软删除、替代与撤销保留正文、原因和历史 | 用户明确认为“错误的经验也是经验”；过去尝试过什么、为什么放弃，对后续 Agent 有价值 |
| 修改粒度 | 以决定或待办条目为单位，使用稳定 ID、状态和修订号 | 物理行不能很好表达多段正文、列表和代码块；只靠全文替换又容易覆盖其他会话的进展 |
| 人工编辑 | 继续使用 Markdown，并提供条目维护界面 | 用户需要继续方便地查看、编辑文档，不希望为了结构化而手工维护逐行 JSON 等数据格式 |
| 工具与 Skill 分工 | Harness 校验修改、状态、版本和落盘，Skill 指导何时记录及如何表述 | 并发和数据完整性适合由工具保证；事实是否核实、用户究竟决定了什么，需要结合任务语境判断 |
| 旧文档处理 | 按需精确纳管已有段落，不批量推断旧条目的性质或状态 | 避免一次迁移就重新解释整份历史，也不因升级插件直接改写真实项目文档 |

默认全文注入的选择允许以后重评，但当前没有采用语义检索、自动重要性筛选或硬 token 截断。未软删除的已完成待办继续保留。完整读取和历史恢复仍然可用，省略首轮背景中的失效条目不会移除它们的正文。

受管理条目在整文精简中由 Harness 原样保留，模型整理其余正文，防止整理时丢失 ID、替代关系、原因或待办状态。这个选择也有边界：受管理条目占多数时，整理可能无法继续缩短。若以后确实出现这类负担，再讨论如何归档条目，同时保留可读取的错误经验与引用关系。

## 2026-11-05：第 5、6 点先完善 Skill

### 区分事实、决定、授权和推测

风险来自相同段落中混用了不同性质的信息：“8 个实例健康”是一次状态观察，“采用某方案”可能是决定或建议，“用户批准同步”则涉及具体操作许可。后续 Agent 若把建议写成已决定，或把历史一次授权扩展为持续授权，文档就会偏离原始对齐。

本轮先在 Skill 中给出明确写法和示例，继续使用四个分区。授权写明对象、动作、范围、来源和实际约定的有效条件；缺失的信息如实记录。事实和推测在容易混淆处说明性质，不要求逐句标注。

暂不增加新区域、强制类型字段或新的权限系统。用户希望按最简单有效的方式改进；当前更需要约束记录语义，而不是继续扩展文档架构。工具仍维护已有条目的状态和历史，记录授权本身不会扩大当前任务的授权。

### 核实时间和证据来源

线上状态有时间范围，文档却会经历复制、润色和精简。若把编辑日期当作核实日期，历史健康快照就会被不断包装成当前事实；若把 MR、构建或申请回执直接写成上线完成，也会丢失验证范围。

因此要求会影响后续执行的状态保留最后实际核实时间、核实范围及证据入口。仅整理文案时沿用原日期；重新核实后才更新；没有取得时间或证据就注明缺口。临时文件和历史快照注明性质，避免后续把它们当作当前在线依据。

本轮通过 Skill 规范完成，不增加自动过期判定、后台线上核查或每句话必填时间的机制。是否需要重新验证，结合后续任务与已有证据判断，避免每次读取文档都触发额外查询和记录负担。

## 2026-11-05：原生加载需要验证实际上下文

用户希望 Skill 和命令随 Harness 同版本分发，省去全局软链，并明确要求保留原生 Skill 加载行为。此前提出的 developer instructions / system prompt 追加走另一条指令路径，这次没有把它当作原生 Skill 的替代实现。

隔离验证发现，Codex 0.166.0 接受独立 `skill` 输入后可以正常完成 turn，但未发现的 Skill 正文没有进入模型请求。先注册隔离 daemon 的搜索根、再使用其返回的规范路径才成功；macOS 同一文件的路径别名也出现过未加载的情况。Claude 的会话本地插件、显式 Skill 调用和恢复则通过验证。

这一步曾暂缓正式接入：生产使用共享 daemon，不能为本功能擅自替换全局搜索根。当时额外把“其他会话连元信息也不能发现”当作要求，超出了用户原意。这个结果再次说明，接口返回成功、列表可见和正文真正进入上下文需要分别确认。方法与结果见 [原生 Skill 加载验证](../../../docs/project-doc-native-skill-validation.md)。

### 同日后续：共享发现可以保留，主动加载按绑定控制

用户指出，原有 `~/.codex/skills/project-doc` 全局软链已经会被其他会话发现，发现本身没有问题。因此采用应用随包分发、原生发现与调用：Git 继续维护唯一源码，应用管理自身版本资源和命令，不再依赖用户拉取源码 checkout 或手工更新全局命令。Codex 使用专属名称 `harness-project-doc`，只调整分发副本的名称以避开旧安装；Claude 通过会话插件加载原始 project-doc Skill。其他 Skill 的配置和旧链接保留。

这里控制的是 Harness 是否主动调用正文：仅绑定会话首次使用当前版本时调用，成功发送后记住，恢复不重复。其他客户端仍可自行发现、选择该 Skill，读写工具继续校验项目与会话绑定，不因发现而取得写权限。合并 PR 只更新代码，应用需构建安装后才使用新资源。

追加验证还发现，Claude 多文本块或图片排在文本后时，即使带斜杠命令也可能没有展开 Skill。改为图片在前、命令与全部文本合成最后一个文本块后，原生正文、原始请求、项目背景和图片均进入本地假模型请求，恢复也保留正文。选择原生加载不仅是接口形式一致，还需要验证真实上下文。

## 后续迭代如何使用这份记录

修改行为时先查看相关取舍，确认原问题是否仍存在、是否出现了新的使用证据。确需改变时记录日期、新原因及替代了哪项取舍，保留旧背景；不要把历史方案直接恢复成当前执行要求。

当前可执行规则只维护在 [SKILL.md](SKILL.md)。实现边界见 [项目文档条目维护](../../../docs/project-doc-entries.md)，项目长期约定见 [项目架构](../../../.harness/architecture.md#项目文档维护)。本文保留决策依据，不复制整份操作协议。
